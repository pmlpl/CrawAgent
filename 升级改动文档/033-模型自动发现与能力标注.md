## 〇、价值

- **改动前**：用户手打模型名（易错字、不知道厂商有什么）；接入接口后无法知道哪个模型支持图片输入——浏览器子 Agent 配了文本模型就盲跑（032 实测：glm-5.2 纯绿图答空、纯红图答"黑"）。
- **改动后**：填好 Base URL + Key 后一键拉取该端点的全部模型名点选回填；每个模型带能力徽章（视觉 / 文本 / 未验证），未验证的一键探测；浏览器子 Agent 不手配时自动挑池中第一个已验证视觉模型，全程免配置。

## 一、背景与问题

1. 现状模型接入全靠手填模型名；`GET /v1/models` 是 OpenAI 兼容标准端点，但前端没有入口。
2. 能力元数据是行业空白：`/v1/models` 只返回 id，不标注是否支持图片输入。032 实测确认配错模型的代价真实存在（browser-use 默认 `use_vision=True` 每步发截图，文本模型收图**不报错但内容不进上下文**——纯绿图答空、纯红图答"黑"，Agent 靠 DOM 文本盲操作）。因此探测判定标准必须是"**答对颜色才算视觉**"，"API 没报错"不是信号。
4. **browser-use 0.13 拿模型动作不用 function calling**：靠 OpenAI `response_format: json_schema` 强制结构化输出（.venv `browser_use/llm/openai/chat.py:225/256`）。子 Agent 模型要过**两关：看图 + JSON 结构化输出**；中转站对 response_format 透传参差，"视觉过了但 JSON 挂了"的半残模型是真实风险。glm-5.2 链路 JSON 关已实测通过（browser-use 跑得动），缺视觉。
3. 现状子 Agent 模型是三档死规则（手配 > env > 主模型），不会从模型池里自动挑视觉模型。
4. 视觉探测的手工方法（发纯色图问颜色）已在 032 调研中人工验证可行，本变更把它工程化。

## 二、目标

1. 「模型」页签添加/编辑模型的表单加「获取模型列表」按钮：按 Base URL + Key 拉取该端点全部模型，点选回填模型名。
2. 模型表新增「能力」列：**两维徽章**（视觉 ✓/✗ + 结构化输出 ✓/✗，未验证显示待测）；每行「测试」按钮一次跑两维探测（看图 + JSON Schema 输出），结果展示**模型原话**（如"回答'黑色'→ 无视觉"）。另保留**手动勾选覆盖**：视觉列可手动勾选（默认不勾），用于用户已知中转映射真相的场景，勾选状态与探测结果分开标记。
3. `browser_use_navigate` 的模型挑选升级为四档：手配（032 三字段）> env 兜底 > **池中第一个两维全过的模型** > 主模型。结构化输出不过的模型即使视觉过也不自动选（browser-use 跑不动，比盲跑更糟）。
4. **不做**：按任务智能路由模型（browser-use 任务一律默认要视觉，一刀切规则）；非 OpenAI 兼容端点的发现；探测的批量自动化（只做单模型手动按钮）。

## 三、方案设计

### 3.1 后端：模型发现与探测端点

- `POST /api/models/discover`：body `{base_url, api_key}` → 服务端代发 `GET {base_url}/models`（OpenAI 兼容，超时 10s）→ 返回 `[{id, owned_by}]`。失败给人话错误（连不上 / 401 / 404 非兼容端点）。
- `POST /api/models/probe`：body `{base_url, api_key, model}` → 一次跑两维探测，返回 `{vision: bool, vision_reply: str, structured: bool, structured_reply: str}`：
  - **视觉**：发 100x100 **纯青色 (0,180,180)** 图问"这张图是什么颜色？只答颜色词"，`max_tokens=30`、超时 20s → 回复含 青/cyan/蓝绿/青绿 视为视觉；空回复/其它颜色/报错视为非视觉。选非常规色防推理模型瞎猜碰对。
  - **结构化输出**：纯文本消息 + `response_format: json_schema`（schema 要求 `{"answer": string}`）→ 能返回可解析 JSON 即通过；报错（400/不透传）即失败。
  - 探测结果缓存（见 3.2），重复探测覆盖；**结果必须带模型原话返回**（前端展示判定依据）。

### 3.2 能力缓存

- 探测结果持久化到模型池配置（存取方式跟随现有模型池数据结构实施时对齐，键 `vision: true/false/null(未验证)`、`structured: 同`、外加可选的手动勾选覆盖键）。
- 内置 pattern 预标注表（新文件 `crawagent/llm/capabilities.py`）：glm-4v / qwen-vl / qwen2-vl / gpt-4o / gpt-4.1 / claude-3+ / gemini-1.5+ / llama-vision / pixtral / internvl 等视觉线命名规律 → 初始标"视觉（推测）"；显式探测结果永远覆盖 pattern 推测。实施时校准表内容。

### 3.3 子 Agent 四档挑选（tools/advanced_tools.py）

032 的三档前插一档、后留一档：

1. 032 手配三字段（settings）非空 → 用手配；
2. `os.environ` 的 `BROWSER_USE_LLM_*` 兜底；
3. **模型池中第一个 `vision === true` 的模型**（复用其 provider 的 base_url + key）；
4. 主模型（现状，盲跑）。

挑选结果写进工具返回头部一行（如 `[子Agent模型: glm-4v-flash (vision)]`）让用户可感知。

### 3.4 前端（SettingsModels.vue）

- 添加/编辑表单：Base URL + Key 非空时显示「获取模型列表」按钮 → 拉取 → 下拉点选回填模型名。
- 模型表新增「能力」列：两维徽章（视觉 / 结构化输出，绿✓灰✗黄未验证）+ 行内「测试」按钮，测试完成后展示模型原话与两维判定；视觉列附手动勾选框（默认不勾，勾选即用户声明，可被测试复核覆盖）。
- 浏览器子 Agent 卡片（032）的模型名输入升级为下拉（池内模型 + 两维徽章，两维全过的排前），保留手输自定义。

### 3.5 测试

- 后端：discover 成功/超时/401/404 分支；probe 两维判定（mock：视觉 青→true/"黑色"→false/空→false；结构化 可解析 JSON→true/400→false）；capabilities pattern 表；四档挑选优先级（含两维全过才自动选、无合格模型回落主模型）。
- 前端：获取按钮流、徽章渲染、探测按钮、子 Agent 下拉。
- 基线计数同步。

## 五、验证方式

1. `uv run pytest tests/ -q` 与 `cd web && npm test && npm run build` 全绿（含新增）。
2. 对 `http://100.83.19.7:8085/v1` 点「获取模型列表」→ 返回该端点实际模型清单并可点选回填。
3. 对 glm-5.2 点「测试」→ 预期两维结果：vision=false（原话类似"黑色"/空）+ structured=true，与 032 人工实测互相印证；徽章与原话展示正确。
4. 模型池接入一个真视觉模型（如 GLM-4V 线）→ 测试两维全过 → `browser_use_navigate` 不手配时自动选中它，返回头标注 `[子Agent模型: ... (vision)]`；浏览器任务表现从"盲跑"变"看图操作"。
5. 池内无两维全过的模型时 → 回落主模型，行为与 032 一致。
