## 〇、价值

指挥官日常真实使用 CrawAgent 时，Agent 常犯「不影响结果但没守契约」的软违规——比如该走内置工具阶梯却直接写脚本、抓完该问存档没问、报错后同参数原样重试。这些违规：

- **改动前**：只有两种途径暴露——撞上评测集预设用例，或指挥官肉眼碰巧看到。真实会话里的违规无人在场、无记录、无人修。
- **改动后**：一个离线审计脚本扫全部真实会话的持久化行为记录，对照 system.md 契约出一份违规报告落盘；指挥官对 AI 会话说一句「看审计报告」，AI 读报告 → 判定真问题/误报 → 写规格修复 → 评测集加回归用例防复发。真实使用从此持续产生「行为改进账本」。

## 一、背景与问题

1. **真实会话的行为记录已经全量落盘，但无人对账**：会话消息（含每条 AIMessage 的 tool_calls 名称+参数、每条 ToolMessage 的执行结果）经 LangGraph checkpointer 持久化在 `sessions_db_path` sqlite（`crawagent/storage/checkpointer.py`，默认 SqliteSaver；会话路由 `crud.py` 就是从 `state.values["messages"]` 读历史回放给前端的）。注意 EventLog（`crawagent/web/event_log.py`）是纯内存逐轮事件，重启即丢，**不能**作审计数据源。
2. **契约条款多、执行全靠模型自觉**：system.md 有脚本阶梯（连续失败必须换脚本、SPA 壳直换脚本、L1-L3 自愈阶梯）、ARCHIVE-ASK（多页抓完当轮必问存档）、MCP ADMIN（add 前必 list 防重名）、Cookie 索取必须走 ask_user 等硬规则。041 评测证明这些规则在预设场景下模型会稳定违反（三个稳定 FAIL），真实会话没有理由例外——只是没人看。
3. **指挥官原话诉求（2026-10-03）**：「我使用的时候出现问题你可以看到，问题可能不影响使用，只是该做的没做，比如抓取网站没按要求使用工具而是直接写脚本。这些问题我可能不会看到，但是你能看到。」
4. 评测集（040/041）是离线考试（假工具桩、预设场景），测「会不会」；真实使用的「实际干活守不守规矩」目前是盲区。

## 二、目标

1. 新增 `scripts/audit_sessions.py`：离线、只读扫描 checkpointer sqlite 的全部（或最近 N 天）会话消息流，按确定性规则判违规。
2. v1 规则五条（见 §3.2），全部字符串/序列运算，**不用 LLM 当裁判**。
3. 违规报告落 `data/audits/audit.md`（追加式，每次扫描一个带时间戳的小节）+ stdout 摘要；报告读者是「下一个 AI 会话」，每条违规自带会话定位 + 证据 + 判读建议。
4. 「待判读」机制：置信度低的命中单独归节，防止误报刷屏变成狼来了。

**不做**（划界）：
- 不做在线拦截/中间件——审计纯旁路，绝不影响运行时行为与性能。
- 不做 UI 徽章/推送——报告受众是 AI 会话，不是人。
- 不做自动修复——修复走既有规格流程。
- 不做 redis checkpointer 后端支持（本机 sqlite，碰到直接退出并说明）。
- 不做 LLM 语义判读（「脚本写得对不对」这类问题不碰，只查序列契约）。

## 三、方案设计

### 3.1 数据源与轮次切分

- 用 `SqliteSaver` 打开 `settings.sessions_db_path`（与 `build_checkpointer` 同一路径构造，只读用途），从 checkpoints 表取 distinct thread_id，逐会话拉 `state.values["messages"]`（同 `routers/sessions/crud.py` 的读取方式，不另造存储）。
- 轮次切分：以 HumanMessage 为界，一轮 = 用户指令 + 其后连续的 AIMessage(tool_calls) / ToolMessage 序列。会话标题复用 `meta_store.get_session_title`。
- 默认只扫最近 7 天（按 checkpoint 时间戳），`--all` 全量，`--sessions <id,id>` 指定会话。天数实施时用真实数据校准。

### 3.2 v1 规则集（五条，判据与 eval_cases 同一契约语义）

| 规则 | 判定逻辑 | 已知合法例外（天然不误报的依据） |
|------|------|------|
| R1 SCRIPT-FIRST-NO-PROFILE | 会话内第一次 run_custom_script 之前，既无 list_site_profiles 调用，也无任何内置工具失败（ToolMessage 含 error/失败特征） | 有档案（list 在前）→ 契约明确允许脚本直取；有失败在前 → 「first sign of failure」合规；壁纸站等特例都要求先调对应工具，天然排除 |
| R2 ARCHIVE-ASK-MISSING | 一轮里列表/抓取类工具成功返回（extract_list_paged / extract_from_html / crawl_webpage 等返回非空结果），轮内既无任何 ask_user 调用也无 save_record | 锚「有没有 ask_user」而非锚问句文本——041 实测 glm-5.2 意译问句概率约一半，锚文本必误报；用户拒存（ask_user 在）不违规 |
| R3 SAME-ARGS-RETRY | 会话内同工具同名+同参数（args JSON 规范化后相等）出现两次及以上，且前一次结果为失败 | L1-L3 自愈阶梯要求换 UA/代理/路线；同参数重试本身就是契约禁止项 |
| R4 MCP-ADD-NO-DUP-CHECK | add_mcp_server 调用时，本会话此前的工具序列里没有 list_mcp_servers | 041 评测 10 号案例同一判据 |
| R5 COOKIE-NO-ASK | 微信读书类工具的 ToolMessage 报 Cookie 未配置类错误后，本会话再无 ask_user，且又调用了同类工具 | 报错后走 ask_user 索取是 system.md 硬规则（041 评测 14 号） |

- 每条命中记 `confidence: high/low`：R1 中若失败与脚本疑似不同目标域（从 args 的 url 抽域名字符串比对，仅提示性），降 low；R5 一律 low。low 全部进「待判读」节。
- **首轮必须跑真实历史校准误报率**，再定各规则的去留与措辞——这是硬门槛（§五.3），不是参考。

### 3.3 报告格式

- `data/audits/audit.md` 追加小节：`## <扫描时间> （范围：最近 7 天 / all / 指定 id）`，下分「违规（high）」「待判读（low）」两节；每条一行式：
  `- [R1] 会话"<标题>"(<sid 前 8>) 第 N 轮 | 证据: 首次脚本前 0 次档案查询、0 次失败 | 建议: 核对是否有跨会话档案依据`
- stdout 摘要：扫描会话数、轮次数、各规则命中数、报告路径。
- data/ 已在 .gitignore，报告不入库。

### 3.4 与评测集的关系

同一契约两处执行：评测集管「预设场景会不会」，审计管「真实使用守没守」。凡审计修掉的行为问题，必须同步在 `eval_cases.py` 加回归用例（或已有用例却放行的，判据要修）——防止修一处漏一处。

### 3.5 边界与回退

- 空 messages、无 tool_calls 的纯对话会话：跳过，不计违规。
- checkpoint_backend=redis：打印说明后退出码 2，不扫描。
- 消息结构异常（非 list、未知类型）：跳过该轮并在报告尾注「N 轮解析失败」，不中断。
- 审计脚本自身异常：不允许写半份报告——先算完内存再一次性落盘。

## 五、验证方式

1. `uv run pytest tests/ -q` 全绿（776 基线 + 本变更新增）；`cd web && npm test` 全绿（前端无改动，保险跑）。

3. **真实数据校准（硬门槛）**：对真实 sessions_db 跑 `--all`，逐条核对命中是否真违规，记录误报率与误报样本；据此校准规则措辞/置信度后再定稿。若某规则误报率过高且无法收紧，砍掉该规则并在实施记录说明——宁缺毋滥。

## 八、实施记录（2026-10-03）

### 怎么做到的（人话版）

给 CrawAgent 装了一个「监工」：`scripts/audit_sessions.py` 离线只读扫描 checkpointer 的 sqlite（`data/sessions.db`），把每个会话的完整消息流反序列化出来（与聊天页回放历史同一条读取链路，EventLog 内存态不可用），按用户消息切轮，然后用五条确定性规则查行为流水——脚本先行无档案、抓完不问档、同参数重试、MCP 加前不查重、Cookie 不索取。报告以带时间戳的小节追加落 `data/audits/audit.md`，每条违规自带会话标题 + id 前 8 位 + 轮次 + 证据 + 判读建议，指挥官对 AI 会话说一句「看审计报告」即可触发判读流。全程纯旁路：URI 只读打开检查点库，不写任何文件、不影响运行时。

### 验证结果（对照 §五）

1. **pytest 全绿 809**（776 基线 + 33 新增）；`npm test` 80 vitest 全绿（前端零改动，保险跑）；000-目录契约测试 6 例全绿。
2. **桩会话双向测试**：33 例全绿——五规则命中与合法例外（档案在先/同域失败在先/ask_user 在轮/用户拒存/「本会话不再询问」/前次成功/参数不同/list 在先/ask_user 隔在中间）均按预期放行或命中。
3. **真实数据校准（§五.3 硬门槛）**：对真实 sessions.db `--all` 首扫 **15 会话 / 68 轮，原始命中 15 条，逐条人工判读 9 条误报（60%）**，全部定位到根因并收紧：
   - 失败签名漏配：android 工具「`ERR:`」前缀、browse_and_crawl「`Browse failed`」前缀未识别 → 失败被当成功 → 补入签名表；
   - 认证墙输出（「需要登录…」开头 120 字符）被当抓取成功 → 加认证墙失败判定（AUTH/PAYWALL 阶梯管辖，无可用内容）；
   - R2 触发集过宽：`download_*`/`extract_social_media` 是用户自取的媒体/元数据、非知识库候选 → 移出触发集（回到规格「列表/抓取类」口径）；
   - R2 轮中命中误报：契约禁的是「抓完**就结束回合**不问」，抓完继续写脚本加工 = 任务未收尾 → 收紧为「当轮以抓取收尾才判」；
   - R1 域名比对降级过严：失败与脚本任一侧抽不出域名（如本地文件分析任务）被误降 low → 改为两侧都抽出且互不相交才降级；
   - R1 未豁免用户指令：用户明说「写一个脚本…」时脚本直跑是遵从用户 → 加豁免标记表。
   **校准后二扫 7 条（R2=5 / R3=2），逐条复判：R2 五条全是契约可辩护的真违规**（抓取完成当轮收尾却未 ask_user 问档，其中 1-2 条边界：任务被登录墙打断后的创造性绕路抓取）；**R3 一条真违规**（create_session 报「not a valid tool」后同参数盲重试）**+ 一条边界**（用户推动的 adb 重查，按规格「会话内同参数重试」字面仍命中，交 AI 判读环节裁量）。**无一条规则因误报收不住被砍**；R1 校准后 0 命中（规则保留——正是指挥官点名的违规类型，本轮真实历史恰好无此类违规）；R4/R5 零命中系真实历史无 MCP 添加/微信读书会话，判据锚 040 评测 10/14 号既有契约语义，如实注明「未在真实数据验证」。
4. **使用流**：默认 `uv run python scripts/audit_sessions.py` 已产出 `data/audits/audit.md`（最近 7 天窗口：2 会话 / 0 命中，报告含违规/待判读/统计三节）。对话式触发的真机验收（§五.4）留指挥官。

### 说明

- **与规格偏差 1（笔误对齐）**：R2 触发器规格原文写「extract_from_html」，实际工具名是 `extract_content`，按真名实现。
- **与规格偏差 2（校准驱动的措辞收紧）**：R2 从「轮内出现成功抓取即判」收紧为「当轮以抓取收尾才判」——不是放松行为断言（合法例外全保留），是把「任务被打断/抓完继续加工」的误报清干净（首扫 9 误报中 2 条源于此）。
- **已知局限（如实记录）**：`fetch_rss_feed` 的 20 条列表成功不在 R2 触发集（真实首扫出现过此形态，宁缺毋滥暂不纳入）；R3 按规格锚「会话内」，跨轮重试也判，用户推动的跨轮重查会命中（边界样本）；smoke-* 冒烟会话与真实使用会话同等参与审计。
- **§3.4 闭环核对**：审计发现的行为问题类型（抓完不问档）已有 040 评测 06/07 号用例覆盖，无「修一处漏一处」缺口，故未新增评测用例；本轮改动全部在审计器自身（校准收紧），未改 system.md 契约与 Agent 行为。
- 顺手修：042 规格 meta 分类原文「Agent 行为与提示词（次要：质量与测试）」与目录九分类不一致（000-目录契约测试拦截），已对齐为「Agent 行为与提示词」（括号注记保留在目录行标题里）。
