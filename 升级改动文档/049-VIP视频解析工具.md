## 一、背景

用户有 VipVideo（Electron 应用，本地安装路径 `C:\Users\MOM\AppData\Local\Programs\VipVideo\`），其核心机制是 URL 拼接：`解析接口前缀 + 视频页URL` → 第三方解析服务返回播放器页面。VipVideo 自身不做任何破解，完全依赖 40+ 个公开第三方解析 API。

当前 CrawAgent 面对用户"解析这个 VIP 视频"的需求时，没有专用工具。用户要么手动去 VipVideo 里操作，要么 agent 用 `run_custom_script` 临场拼脚本——每次拼的 URL 可能错、没有接口列表、没有失败重试。

## 二、价值

- **改动前**：agent 面临 VIP 视频解析需求只能临场写脚本，无解析接口列表，无失败自动换接口。
- **改动后**：agent 调 `parse_vip_video` → 自动遍历 40+ 解析接口 → 返回第一个成功的可播放 URL/流地址。配合 `download_social_media` 可实现"解析→下载"一条龙。

## 三、设计

### 3.1 新建 `crawagent/tools/assets/vlist.json`

从 VipVideo 的 `app.asar` 解包提取，内容：
- `platformlist`：30+ 视频平台（腾讯/爱奇艺/芒果/优酷等，`canvip=1` 标记支持 VIP 绕过）
- `list`：40+ 解析接口（名称 + URL 前缀，如 `https://bfq.txnp.cn/player?url=`）

### 3.2 新建 `crawagent/tools/vip_video_tool.py`

两个 `@tool` 函数：

**工具 1：`parse_vip_video`**
- 签名：`parse_vip_video(video_url: str, parser_name: str = "") -> str`
- 行为：
  1. 加载 `vlist.json` 的 `list`（解析接口列表）
  2. 若 `parser_name` 非空，只试该接口；否则按顺序遍历全部
  3. 对每个接口：HTTP GET `{parser_url}{video_url}`（5s 超时）
  4. 检测响应是否含可播放内容（m3u8/mp4/iframe/video 标签）
  5. 第一个成功即返回：解析接口名 + 可播放 URL + 响应片段
  6. 全部失败返回失败汇总
- 输出格式：
  ```
  ✅ 解析成功（接口：默认A）
  视频页：https://v.qq.com/x/cover/xxx.html
  播放地址：https://jx.txnp.cn/player?url=xxx
  流类型：m3u8
  ----
  响应片段（前500字符）：...
  ```
  或：
  ```
  ❌ 全部 40 个解析接口均失败。
  尝试的接口：默认A, 邦宁, 极速, ...
  视频页：https://v.qq.com/x/cover/xxx.html
  常见原因：视频页 URL 无效/解析接口临时失效/需要登录。
  ```

**工具 2：`list_vip_platforms`**
- 签名：`list_vip_platforms(category: str = "all") -> str`
- 行为：加载 `vlist.json` 的 `platformlist`，按 category 过滤，返回平台名 + URL + canvip 标记
- 用途：agent 知道哪些平台支持 VIP 绕过，引导用户给 URL

### 3.3 两级检测逻辑（复用 VipVideo test-parsers.js 验证过的正则）

**第一级：预筛（prescreen）—— 纯 HTTP，并发，秒级**

对每个接口发 `GET {parser_url}{video_url}`（5s 超时），按以下规则判定：

判死规则（任一命中即跳过该接口）：
- HTTP 不可达 / 超时 / DNS 失败
- 状态码 >= 400
- 响应体 < 200 字节且无视频关键词
- 响应体含失败文本（正则，不区分大小写）：
  ```
  /(解析失败|不支持该|线路维护|资源不存在|该网站暂不支持|视频已下线|parameter error|url error)/i
  ```

判活规则（任一命中即判定该接口预筛通过）：
- 状态码 < 400
- 响应体含视频流 URL（正则）：
  ```
  /\.(m3u8|mp4|ts|flv|mkv|m4s|webm|mov)(\?|#|$)/i
  ```
- 或响应体含播放器标记：`<video` / `<iframe` / `player`

**第二级：浏览器验证（可选，agent 决定是否调用）**

预筛通过的接口，agent 可选用 `browse_webpage` 工具加载页面，检测 `<video>` 元素 + `currentTime` 是否前进。大多数场景预筛足够（预筛通过 → 实际可播率 > 80%）。

### 3.4 解析接口缓存（成功率排序）

缓存文件 `data/parser_cache.json`，记录每个接口的：
- `success_count`：成功次数
- `fail_count`：失败次数
- `last_success_ts`：最后成功时间戳

调用 `parse_vip_video` 时：
1. 先按成功率（`success_count / (success_count + fail_count)`）降序排序
2. 优先试成功率高的接口
3. 成功则更新该接口 success_count + last_success_ts
4. 失败则更新 fail_count
5. 首次调用（缓存为空）按 vlist.json 原始顺序遍历

### 3.5 复用与不复制

- HTTP 请求复用 `social_utils.py` 的 `_resolve` / `DESKTOP_UA` / `MOBILE_UA`
- vlist.json 路径查找复用 015 的三级查找基建（PATH → settings → 常见位置）的思路，但这里文件在包内 `assets/`，直接 `Path(__file__).parent / "assets" / "vlist.json"`
- 输出截断复用 `android_reverse_tool._truncate`
- 并发请求用 `concurrent.futures.ThreadPoolExecutor`（标准库，无新依赖）

### 3.6 不做（边界声明）

- **不做视频下载**：解析出流地址后，下载交给现有 `download_social_media`
- **不做播放器 UI**：CrawAgent 是爬虫框架，不嵌入视频播放
- **不做浏览器验证**：预筛通过即返回，agent 可自行调 `browse_webpage` 做二级验证
- **不做接口自更新**：vlist.json 随版本发布手动更新

## 七、说明

- **与规格的偏差**：① §3.2 原写"顺序遍历、首个成功即返回"，实施改为"并发预筛全部 + 成功率排序取最优"——规格 §3.3/3.4 更新时引入并发与缓存排序后，串行首个成功语义与之矛盾，取更优者；② 成功输出新增"响应片段"行（规格 §3.2 原有、更新时漏掉，实施补回，兼作测试 12 的截断断言点）；③ vlist.json 实际 45 接口（规格写 40+）。
- **实测背景**（2026-10-10 真机预筛腾讯视频《现在就出发第四季》）：40 接口 29 秒筛完，PASS 9 / FAIL 24 / UNKNOWN 11；浏览器验证 M3U8 接口真实播放到 06:40/47:53 完整正片无广告。预筛通过≠100%可播，工具输出已提示 agent 可用 browse_webpage 二次确认。
- **不做**（§3.6 边界）：视频下载（交 download_social_media）、播放器 UI、浏览器级验证（agent 自行用 browse_webpage）、接口自更新（vlist.json 随版本手动更新）。
- **追加混合使用硬规则**（2026-10-11 真机复测后）：爱奇艺《喜剧之王》实测 agent 不调 parse_vip_video 而用 browser-use 硬挖平台原始页 11 分钟无果（流地址 blob 加密）；且预筛通过 13 接口下游节点全失效——"预筛通过 ≠ 实际可播"实锤。故 system.md VIP Workflow 追加：① HARD RULE 禁止 browser 工具直接爬视频平台原始页（browser 只准打开解析服务播放器页）；② Step 2 浏览器验证（video 元素 + currentTime>0），不播依次换备用接口最多 3-4 个；③ 失败兜底阶梯三档。测试断言同步补齐（test_system_md_consistency）。
