## 〇、价值

- **改动前**：记忆与档案没有按会话的物理落点——轮次历史在 checkpointer（sessions.db/redis）、档案在 FTS5 库（knowledge.db），用户在资源管理器里什么都看不见、没法备份单个会话的记忆；项目文件夹被删时用户担心记忆/档案跟着没了（实际在库里，但没人知道）；旧会话数据永久沉底，精华知识从不回流。
- **改动后**：每个会话有 `data/sessions/<会话id>/` 文件夹（人可读、可整个拷走备份），档案存档时同步落 md 快照；项目文件夹删了记忆档案安然无恙（物理解耦）；超过半年不活跃的会话文件夹走「提炼 → 入长期记忆库 → 归档」流程，旧会话精华变成可检索的长期记忆。

## 一、背景与问题

1. 指挥官 2026-10-01 设计裁决（配合 038 的 1:1 锁定）：**一个会话一个项目**；项目文件夹路径删除 → 本会话 AI 写不了产物，**但历史记忆、档案等内容仍存在**——因为有一个专门的会话文件夹（名称 = 会话 id）存储记忆/档案，与项目文件夹物理分离。
2. 现状盘点：`save_record` 只写 FTS5 库（用户不可见）；014 产物目录用「会话标题清洗名」（会随重命名变化，不可作 id）；**没有** `data/sessions/<id>/` 这一层。
3. **存储载体裁决（指挥官问「数据库还是文件夹」，已定混合方案）**：
   - **会话热数据 = 文件夹**：人可在资源管理器直接看、可整个拷走备份；agent 用现成 read_file/save_to_file 读写（零新工具）；清理 = 删目录，物理直观；踩 ADR-0001 的 data/ 约定。
   - **长期记忆 = 数据库**（沿用 008 FTS5 knowledge.db）：记忆的价值在于**能被搜出来**——RETRIEVE-FIRST、BM25、snippet 链路现成；纯文件夹放长期记忆检索会退化成逐文件 grep；提炼产物是结构化条目，天然适合 save_record。
   - 一句话：**文件夹管活着的会话，数据库管死去会话留下的精华。**

## 二、目标

1. **会话文件夹**：`data/sessions/<会话id>/`，会话级记忆/档案快照的物理落点（md 格式、人可读）。
2. **档案双写**：ARCHIVE-ASK 存档案时，save_record 入库 + 同步写 md 快照到会话文件夹（一份进库可检索，一份落盘可阅读可备份）。
3. **长期记忆提炼与清理**：距最后活跃超过 180 天（初值，实施时校准）的会话文件夹 → LLM 蒸馏成知识条目 → save_record 入库 → 目录移入 `data/sessions/_archived/`。实际删除永远由用户手动执行（_archived 即终点，不做自动物理删除）。
4. **不做**：自动定时清理器（启动时只统计提示，不自动动手——MCP_AUTOSTART 教训：任何批量删文件必须用户显式触发 + ask_user 确认）；checkpointer 轮次历史的迁移/提炼；项目文件夹里产物的移动；会话重命名后目录改名（id 恒定，改名不影响）。

## 三、方案设计

### 3.1 会话文件夹落点与结构

- 路径：`data/sessions/<sid>/`（sid = ctx_session_id 全值，非截断——与 014 的 sid[:8] 兜底区分，本层是系统资产必须全局唯一）。
- 惰性创建：首次写档案快照/记忆快照时 mkdir（不搞会话启动即建空目录）。
- 结构原则（实施时可微调）：`<sid>/archive/<主题>.md`（档案快照）、`<sid>/memory/`（记忆快照，预留）；每个 md 头部写元信息（会话 id、归档时间、来源 URL/主题），保证脱离库也能读懂。
- sid 清洗沿用 sanitize_dirname 思路（id 本身安全，防御性保留）。

### 3.2 档案双写（唯一的新写入链路，克制不过度设计）

- save_record 入库成功后：把档案正文（含元信息头）写 `<sid>/archive/<清洗后的主题或标题>.md`，重名序号与上传同款（-1/-2）。
- 双写失败的降级：库成功、盘失败 → 工具结果里注明「已入库但本地快照写入失败」（不回滚库）；盘成功、库失败 → 现有错误语义不变。
- 记忆快照不做自动注入——agent 需要时用 save_to_file 自主落（system.md 引导一句即可），避免每轮都写盘的性能/噪音。

### 3.3 清理统计（只读，不删任何东西）

- 启动时 + 设置页打开时统计：`data/sessions/` 下各 <sid> 文件夹的最后活跃时间（取夹内文件最新 mtime；**或** meta_store 加 last_active_ts 列——两案实施时选，前者零 schema 变更，后者准）。
- 超 180 天的列入「可清理」清单：设置页新卡片（放「数据管理」区块，复用 034 高级页卡片模式）展示列表（会话标题 + 大小 + 最后活跃）。
- 会话标题从 meta.db session_titles 反查（文件夹名是 id，展示要人话）。

### 3.4 提炼与归档（用户显式触发）

- 卡片上「清理并提炼」按钮 → ask_user 选择题确认（批量删/移动文件硬规则）。
- 流程：读该会话文件夹全部 md → LLM 蒸馏成知识条目（每条：主题 + 要点 + 来源会话 id；条数按内容量 3-15 条）→ 逐条 save_record（加来源标记，如 record 元数据带 session_id）→ 全部入库成功后把整个 `<sid>/` 目录移动到 `data/sessions/_archived/<sid>/`。
- 蒸馏失败（LLM 错误/超时）：**不动文件夹**，报错重试；宁可留着下次再提炼，不可丢。
- 提炼调用走现有 LLM 通道（get_llm），长内容分段；进度走 report_progress（与 037 下载进度同链路）。

### 3.5 system.md / wiki 同步

- save_record 描述补「同时写入会话归档文件夹」一句；工具条数不变（无新 @tool，除非实施时决定把「清理提炼」做成工具而非路由——**规格倾向路由 + 设置页**，工具会让 agent 有权触发删文件，风险大）。
- CONTEXT.md 新术语：会话文件夹、长期记忆、_archived。

### 3.6 测试

- 后端：双写（save_record 后快照落盘 / 盘失败降级 / 重名序号）；统计（超期判定 mtime / 标题反查）；提炼（mock LLM 返回条目 → save_record 调用断言 → 目录移入 _archived / 失败不动）；路径清洗。
- 前端：卡片渲染、超期列表、确认链路。
- 基线：038 完成后的 pytest/vitest 基线起算（实施时以当时全量为准登记）。

## 五、验证方式

1. 全量测试全绿（以实施时基线为准登记计数）。
2. 真机：ARCHIVE-ASK 存档案 → `data/sessions/<sid>/archive/*.md` 出现且人可读（元信息头完整）；资源管理器整个拷走该文件夹仍可读。
3. 项目解耦：删除项目文件夹（038 失效态）→ 会话文件夹与检索不受影响。
4. 清理统计：造一个 mtime 超半年的会话文件夹（或临时调小阈值）→ 设置页卡片出现在超期列表。
5. 提炼归档：点「清理并提炼」→ ask_user 确认 → 完成后 `search_knowledge` 能检索到蒸馏条目（来源含会话 id）→ 原目录已移入 `_archived/`；蒸馏中途断 LLM → 目录原封不动。
6. 删除兜底：全程无任何「静默物理删除」——_archived 目录由用户手动清理。

## 八、实施记录（2026-10-01）

### 怎么做到的（人话版）

1. **会话文件夹**：新模块 `crawagent/tools/session_folder.py`——`data/sessions/<sid>/`（sid 全值，sanitize_dirname 防御性清洗，路径穿越自然失效），惰性创建（首次写快照才 mkdir，`archive/` 子目录一并建，`memory/` 预留）。`write_archive_snapshot` 落 md 快照：头部元信息（会话 id / 归档时间 / 来源 URL）保证脱离库也能读懂，重名序号 -1/-2（与上传同款）。统计函数 `iter_session_folders`（跳过 `_archived`）/ `folder_last_active`（夹内文件最新 mtime）/ `folder_size` 离线纯函数。
2. **档案双写**：save_record 入库成功且本会话有会话文件夹时，同步把同一份正文落 `<sid>/archive/<清洗标题>.md`；盘失败不回滚库，结果串注明「已入库但本地快照写入失败」；无会话上下文（CLI/直调）跳过快照，行为同改前。save_record 内部的 INSERT 抽成 `_insert_record` 共用路径（FTS 触发器对两种入口同样生效）。
3. **提炼与归档**：新路由 `crawagent/web/routers/data_manage.py`——`GET /api/data/sessions/overview`（只读统计：sid + meta.db 标题反查 + 大小 + 最后活跃 + 是否超期 + 归档计数）；`POST /api/data/sessions/{sid}/distill` 读该会话文件夹全部 md → 按 3 万字符分段（最多 6 段）调 get_llm 蒸馏成 {topic, points} 条目 → 单事务逐条直插 crawl_records（platform=长期记忆、session_id=来源会话、url=session://<sid>）→ 全部成功后整夹移入 `_archived/<sid>/`（同名加序号绝不覆盖）。任何一步失败（LLM 错误/解析失败/入库失败）→ 文件夹保持原样，宁留勿丢。路由用 sync def 让 FastAPI 进线程池，长蒸馏不堵事件循环。启动时 `_startup_prune` 线程顺带调 `log_stale_sessions()` 只报数提示，不自动动手。
4. **设置页卡片**：高级页签新增「会话记忆管理」card——挂载即拉 overview，超期会话列表（标题/大小/日期），每行「提炼并归档」按钮走**两步确认**（点按钮 → 行内确认条「确认提炼？…将蒸馏入库并移入 _archived/」→ 确认才调端点），完成后刷新统计；活跃/已归档计数常显。
5. **搜索闭环**：蒸馏条目与 save_record 同表同 FTS 触发器，`search_knowledge` 直接可检索（测试验证短条目不被误杀）。

### 说明（与规格偏差）

- **ADR 编号 0008 非 0004**：规格成文时 ADR 目录只到 0003，实际已有 0001-0007，按序列落 `0008-session-folder-hybrid-storage.md`。
- **「最后活跃」选 mtime 方案**（规格留二选一）：会话文件夹的活跃 = 快照写入（039 本层唯一写入口），文件 mtime 恰是准确语义，且零 schema 变更、统计纯函数离线可测。meta_store 加列方案对「会话没写过快照」的场景反而无解。
- **确认交互用前端两步确认，非 ask_user 选择题**：ask_user 是聊天页「AI 问用户」的 WS 事件机制（落聊天 items），设置页触发的 REST 流程接不进该通道。行内确认条（确认/取消）等价实现「批量动文件必须用户显式批准」的硬规则语义；后端 distill 端点因此不做二次确认——按钮点击即用户显式触发。
- **提炼进度未走 report_progress**：report_progress 挂在「当前活跃工具」上（agent 轮次内由 with_progress 包装器 start_tool），REST 路由无此上下文，强行走会被心跳投递到不确定的会话。提炼是同步操作（前端按钮转圈 + 完成后刷新统计），时长由分段上限（6 段 × 3 万字符）控制。
- **蒸馏条目免五关质量过滤**（insert_longterm_record 直插）：五关（长度 <200 字等）为爬取正文设计，会误杀蒸馏短条目；与 save_record 共用同一 `_insert_record` 插入路径 + FTS 触发器，检索链路完全一致。规格「逐条 save_record」按其意图（入同一知识库）实现为同一表的免关通道。
- **新增 tests/conftest.py 全局隔离**（规格未列）：实施中发现 save_record 双写让既有测试把快照写进真实项目 data/sessions/（ContextVar 跨测试泄漏 + 会话文件夹落点未隔离），autouse fixture 每测试清空会话上下文 + 把 session_folder 落点 patch 到 tmp_path，已验证 data/sessions 不再被测试重建。
- 本变更已随本 commit 入库（代码与文档同批）。
