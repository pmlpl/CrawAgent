## 〇、价值

- 指挥官在 `localhost:8006` 设置的壁纸，换用 `127.0.0.1:8006` 打开后消失——**改动前**：壁纸存浏览器 localStorage，按 origin 隔离，换个地址/换个浏览器就"没有壁纸"；**改动后**：壁纸存服务端 `data/`，任何地址、任何浏览器看到同一份。
- 附带消灭一个大文件配额坑：localStorage 约 5MB 上限，大壁纸设置失败或刷新即丢。

## 一、背景与问题

1. **origin 隔离**：浏览器把 localStorage 按协议+主机+端口隔离。`localhost` 与 `127.0.0.1` 是两个主机名，存储完全独立。这是浏览器标准行为，代码没有 bug——错在把壁纸这种"希望全局一致"的数据放进了 origin 绑定的存储。
2. **5MB 配额雷（更早一次发作）**：base64 按 UTF-16 计费约等于原始字节的 2.7 倍，MB 级壁纸必然塞爆；且当年 setBg 的 catch 静默吞错，被用户误读为"格式不支持"（2026-09-06 早间已修：canvas 压缩 + 失败显式报错，commit `9ec6f88`——但压缩只是止痛药）。
3. 决策经 grilling 会话拍板（方案 B 治本，否决了"重定向归一 origin"的治标案与"文档约定固定地址"的零成本案），结论沉淀为 **ADR-0001**。

## 二、目标

1. 背景图与遮罩浓度持久化到服务端 `data/`，跨 origin、跨浏览器一致。
2. 上传/清除/调浓度全部走后端 API；失败显式报错（沿用"不许静默 catch"的规矩）。
3. **不做**：多壁纸库、云同步、鉴权（本地部署既定无鉴权）。

## 三、方案设计

- **存储**：`data/background.jpg`（图片本体）+ `data/background.json`（遮罩浓度）。前端上传前仍走 canvas 压缩（最长边 1920px、JPEG q0.82，产物约 200-400KB）——压缩的理由从"塞配额"变为"控制请求体与磁盘占用"，所以保留。
- **API**（挂设置路由）：`GET /api/background` 状态（图片 URL 带 mtime 防缓存）、`GET /api/background/image` 图片本体、`POST /api/background` 保存（只认 `data:image/jpeg;base64`，8MB 防御上限）、`POST /api/background/opacity` 浓度（0-95）、`DELETE /api/background` 清除。
- **前端 useBg.js 重写**：启动时拉取（App.vue 首次调用即恢复）；上传立即本地预览、落服务端成功后切换为正式 URL；浓度滑块本地即时生效 + 500ms 防抖再持久化。localStorage 键废弃不删（残留无害）。

## 八、实施记录（2026-09-06）

### 怎么做到的（人话版）

核心只有一句话：**把"壁纸"从浏览器的小抽屉搬进服务端的仓库**。浏览器给每个网址分配独立小抽屉（localStorage），而服务端只有一份 `data/`，谁来看都是它。技术上分三步：前端把压缩后的图片 base64 交给后端、后端解码成字节写进 `data/background.jpg`、前端启动时不再读本地抽屉而是请求 `/api/background` 拿图片地址。遮罩浓度是一个数字，单独放 `background.json`。

两个关键取舍：
- **压缩保留但理由变了**。之前压缩是为了骗过 5MB 配额（绕不过去，只能把图变小）；现在配额不存在了，但 200-400KB 的产物让上传快、磁盘省，所以压缩流程原样保留。
- **图片 URL 带上文件修改时间做"防缓存戳"**。否则换了壁纸浏览器还显示旧图（静态资源缓存），每次保存后 URL 变化强制重新拉取。

### 实际改动

与规格一致，无偏差。范围：后端端点组 + useBg 重写 + 上传流程适配 + 7 个 API 测试。

### 验证结果（对照 §五）

1. ✓ TestClient 全链路（save → state 带 mtime URL → image 字节一致 → clear 回空）。
2. ✓ Playwright 实测与后续多轮截图走查（双主题、双地址访问同一份壁纸）。
3. ✓ 非 jpeg 前缀与坏 base64 拒绝用例通过。
