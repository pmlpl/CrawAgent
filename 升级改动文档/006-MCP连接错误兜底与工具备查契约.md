## 〇、价值

- **改动前**：anything-analyzer 未启动时，Agent 调 `check_mcp_status()` → `_call_mcp` 的 `httpx.post` 抛 `httpx.TransportError`（Windows 表现为 `[WinError 10061] 目标计算机积极拒绝`）→ 裸异常穿透 @tool → 杀死整轮任务。同时 Agent 看到原生 MCP 工具不在工具列表时，直接对用户说"没工具、没法干"，把诊断责任甩给用户。
- **改动后**：连接被拒/超时被 `_call_mcp` / `_ensure_mcp_session` 兜成 `{"error":{"kind":"connection_refused",...}}` 返回，`check_mcp_status` 原有的错误分支接管（自动拉起 / `[MCP_UNREACHABLE]` 引导）。契约侧 system.md 新增 Step 0 工具备查：原生工具缺失时 MUST 调 `check_mcp_status` 诊断 + `ask_user` 拉起，禁止直接放弃。

## 一、背景与问题

1. **裸异常杀任务**：`_call_mcp`（ping 等）与 `_ensure_mcp_session`（initialize 握手）的 `httpx.Client.post` 都无 try/except；服务未起时抛 `TransportError`，`check_mcp_status` 的 `if "error" in resp` 分支根本到不了。
2. **契约无 Step 0**：MCP Capture Workflow 的 Step 1 直接调 `create_session`，但 `create_session`/`navigate`/`cdp_send_command`/`browser_screenshot` 这些原生工具只在 anything-analyzer 运行时才装进工具箱（构建期快照）。Agent 看到缺工具时契约没要求它自检，于是放弃。
3. **入口工具其实永在**：`check_mcp_status` 在 `_SKIP_TOOL_NAMES` 里（不走自动扫描），由 `build_mcp_tools` 无条件塞进 `final`——MCP 没起也能调。所以 Agent 有能力自检，只是契约没教。

## 二、目标

1. `_call_mcp` / `_ensure_mcp_session` 的 httpx 调用包 try/except，`TransportError`（ConnectError/ConnectTimeout/ReadTimeout 等）转成 `{"error":{"kind":"connection_refused","message":...}}`，保留原始 WinError 信息便于排查。
2. `check_mcp_status` 收到 connection_refused 后走原错误分支：`ensure_mcp_started(force=True)` 尝试拉起，失败返回 `[MCP_UNREACHABLE]` 引导。
3. system.md MCP Capture Workflow 新增 **Step 0 工具备查**：原生工具不在列表 → MUST 调 `check_mcp_status` 诊断 + `ask_user` 拉起；IMPORTANT RULES 加"工具缺失不等于放弃"硬规则。
4. **不做**：改 `build_mcp_tools` 的构建期快照语义（原生工具仍只在 MCP 起时装入，靠 reset_agent_cache 下一轮生效）。

## 三、方案设计

- **httpx 兜底**：`_ensure_mcp_session` 的 initialize POST 与 notifications POST 各包 try/except（notif 失败不致命，忽略仍返回 session id）。`_call_mcp` 的请求 POST 兜底后额外 `_reset_mcp_session()`（连接断了 session 可能已失效）。
- **错误字典统一**：`{"error":{"kind":"connection_refused","message":"MCP 连接失败: <原始异常>（anything-analyzer 未启动或端口未监听）"}}`。`check_mcp_status` 现有 `if "error" in resp` 分支自然命中：msg 不含 auth → 走 `ensure_mcp_started` 拉起，失败回 `[MCP_UNREACHABLE]`。
- **契约 Step 0**：在 system.md 的 MCP Capture Workflow 最前加 Step 0，列原生工具名清单；明确"不在列表 = MCP 未运行"，禁止单纯回用户"没工具干不了"。IMPORTANT RULES 补对应硬规则。

## 五、实施记录（人话版）

1. **`_ensure_mcp_session` 兜底**：initialize 的 `httpx.Client.post` 包 try/except `httpx.TransportError`，捕到返回 `(None, {"error":{"kind":"connection_refused","message":...}})`，保留原始异常文本。notifications/initialized 那次失败不致命（session id 已拿到），只打印忽略。
2. **`_call_mcp` 兜底**：请求 POST 包 try/except，捕到先 `_reset_mcp_session()`（连接断了缓存 session 大概率失效，下次重新握手），再返回 error dict。
3. **check_mcp_status 不动逻辑**：它本来就是 `resp = _call_mcp("ping"); if "error" in resp: ...`。现在 `_call_mcp` 返回 error dict 而非抛，这条分支终于能跑到——`ensure_mcp_started(force=True)` 尝试拉起，失败回 `[MCP_UNREACHABLE]` 引导。自动拉起路径恢复设计意图。
4. **system.md Step 0**：在 MCP Capture Workflow 最前加"Step 0 — 工具备查（MUST）"，列原生工具名；明确"不在列表 = MCP 未运行，MUST 调 check_mcp_status 诊断，禁绝甩锅给用户"。IMPORTANT RULES 补同义硬规则。
5. **测试**：`tests/test_mcp_connection_error.py` 三用例。monkeypatch `httpx.Client` 为"实例化即抛"的替身，断言 `_call_mcp` 返回 error dict（含 10061 文本）、`check_mcp_status.func()` 端到端返回含 `MCP_UNREACHABLE` 的字符串。`@tool` 装饰后 `check_mcp_status` 是 StructuredTool，测试用 `.func()` 调底层纯函数。
