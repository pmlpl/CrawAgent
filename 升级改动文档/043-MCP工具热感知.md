## 〇、价值

- **改动前**：聊天里让 AI 加/删/停用 MCP server，工具的回话承诺「下条消息生效」，但实际缓存从未清除（实锤见 §一.2）——原生 MCP 工具下轮根本装不进来，用户被误导后只能去设置页再保存一次或重启后端。外部改 Electron 配置文件（token/开关）同样无感知。
- **改动后**：任何路径改了 MCP 配置（聊天管理工具 / 设置页保存 / 外部改文件 / token 同步漂移），下一轮对话 `get_agent` 自动比对配置指纹、发现变化就地重建工具箱。「下轮生效」从空话变成事实，零手动步骤。

## 一、背景与问题

1. **工具箱构建链与缓存**：`turn_engine.py:215` 每轮调 `state.get_agent(model)` → `_agents` 字典按模型键缓存编译后的 Agent → `graph.agent.get_agent` → `_build_tools()` → `build_mcp_tools()`（消费 `get_settings().mcp_servers` + Electron 配置文件的 enabled/token）。Agent 一旦入缓存，配置怎么变它都无感知——这就是「工具箱是构建期快照」的机制根源。
2. **聊天路径的生效承诺是假的（本次实锤）**：`mcp_admin_tool.py` 的 add/remove/disable 三个管理工具全文件**没有一处调用 `reset_agent_cache`**（grep 实证），而 `add_mcp_server` 成功文案写着「（reset_agent_cache 已触发，原生 MCP 工具下轮装入工具箱）」——描述了一个从未发生的调用。真正清缓存的只有设置页保存路由（`routers/settings/mcp.py:121`）和 `check_mcp_status` force 拉起路径（`mcp_capture_tool.py:408`）。
3. **补丁式重建体验割裂**：check_mcp_status force 重建后还要提示「请让用户新发一条消息触发重建」；用户手动改 Electron 配置文件则完全无人理睬。
4. 指挥官拍板（HANDOFF 043 立项）：配置指纹每轮比对，变了自动重建。

## 二、目标

1. `state.get_agent` 取缓存前比对 MCP 配置指纹，不一致则丢弃对应 Agent 就地重建；**checkpointer 单例不动**（会话状态与记忆无损）。
2. 指纹覆盖 `build_mcp_tools` 实际消费的全部输入：`settings.mcp_servers`（含 enabled/token/url/headers）+ Electron 配置文件内容。
3. 三个管理工具的「下轮生效」文案与实际机制对齐（043 后承诺为真，措辞同步校正）。

**不做**（划界）：
- 不改 `build_mcp_tools` 装配逻辑本身；不动 60s 失败负缓存与 `check_mcp_status` force 路径（二者照旧，指纹门是叠加的兜底）。
- 不做配置变更事件总线/主动推送——轮询比对（一次 sha256 + 小 JSON，微秒级）已够，事件化进 §六。
- 不覆盖 registry 基础工具变化（那是代码变更 = 重启，不属于热感知范畴）。

## 三、方案设计

### 3.1 指纹函数（`state.py` 新增 `_mcp_fingerprint() -> str`）

```python
sha256(json.dumps([get_settings().mcp_servers, electron_cfg],
                  ensure_ascii=False, sort_keys=True))
```

- `electron_cfg` 来自 `mcp_capture_tool._load_electron_mcp_config()`（函数内惰性 import，避免模块级循环依赖；读不到时记 `{}`）。
- 纯函数、毫秒级；每轮调一次成本可忽略。

### 3.2 `get_agent` 指纹门

```python
_mcp_fps: dict[str, str] = {}   # 模型键 -> 构建 Agent 时的 MCP 配置指纹

def get_agent(model=None):
    key = model or "__default__"
    fp = _mcp_fingerprint()
    if key in _agents and _mcp_fps.get(key) != fp:
        del _agents[key]          # MCP 配置变了：丢弃旧 Agent（只丢该模型键）
    if key not in _agents:
        _agents[key] = _build_agent(checkpointer=get_checkpointer(), model=model)
        _mcp_fps[key] = fp
    return _agents[key]
```

- 指纹异常（读 Electron 文件失败等）：按「未变化」处理 + print 警告，**绝不阻断对话轮次**。
- `reset_agent_cache()` 同步清空 `_mcp_fps`（全清语义保持）。
- 重建只换 Agent 对象：`get_checkpointer()` 单例复用，会话记忆连续；`reset_turn_state` 由 turn_engine 每轮在新对象上调用，行为不变。
- DeepSeek prompt cache：工具列表变化自然使前缀缓存失效，与今天重启后重建的成本一致，无额外处理。

### 3.3 文案对齐

- `add_mcp_server` 的「reset_agent_cache 已触发」改为与机制一致的措辞（如「下一条消息自动重建工具箱（配置指纹检测）」）；remove/disable 的「下轮生效」经指纹门后自动为真，逐条核对即可。**043 落地后实施时逐条比对三工具全部用户可见文案与实际行为。**

### 3.4 测试设计

- `_mcp_fingerprint` 表驱动：加 server / 翻转 enabled / 改 token / 改 url / 无关设置变化（不敏感）五组断言。
- `get_agent` 门：monkeypatch `_build_agent` 为计数桩 + `_mcp_fingerprint` 打桩——指纹变化重建（计数+1）、不变复用（计数不变）、重建后新指纹入账；`reset_agent_cache` 清空指纹表。
- 指纹函数异常兜底：Electron 配置缺失/损坏时返回稳定值不抛异常。

## 八、实施记录（2026-10-03）

### 怎么做到的（人话版）

以前 Agent 的工具箱是「构建期快照」：服务起来时照着当时的 MCP 配置装一次工具，之后配置怎么改它都不理。043 给它装了一扇「指纹门」：每次对话取 Agent 前，把当前 MCP 配置（.env 的 server 列表 + Electron anything-analyzer 配置文件，正是 build_mcp_tools 装工具时吃的全部输入）算一个 sha256 指纹，跟上次构建 Agent 时记下的指纹比——不一样就把旧 Agent 扔掉按新配置就地重建。指纹就是一次哈希计算，每轮一次无感。异常兜底：指纹算不出来（如 Electron 文件读取出错）按「未变化」处理只打警告，绝不卡住对话。checkpointer 单例不动——重建只换 Agent 对象，会话状态与记忆连续。

### 实际改动

- `crawagent/web/state.py`：新增 `_mcp_fingerprint()`（`get_settings().mcp_servers` + Electron 配置 → sha256；计算异常返回上次成功指纹）；`get_agent` 取缓存前比指纹，不一致 `del _agents[key]` 就地重建并记新指纹（只丢被请求的模型键，惰性）；`reset_agent_cache` 同步清空 `_mcp_fps`（全清语义保持）。
- `crawagent/tools/mcp_admin_tool.py`：三管理工具回话文案与实际机制对齐——add 基础文案去掉「（reset_agent_cache 已触发…）」改为「配置已落盘并清空 Agent 缓存，下条消息自动重建工具箱…」；add 离线分支「或下轮自动重试装入」改为如实描述（下条消息重建时装入一次；仍未启动则 check_mcp_status 诊断拉起，拉起成功后下条消息装入）；remove/disable 统一补「配置已落盘并清空 Agent 缓存」；模块 docstring 更新为生效双保险（保存即清缓存 + 指纹门兜底）。
- `tests/test_mcp_hot_reload.py` 新增 6 例（§3.4 三组全覆盖）；`tests/test_mcp_admin.py::test_add_http_success` 1 处文案断言同步（「下条消息生效」→「下条消息自动重建工具箱」）。

### 验证结果（对照 §五）

1. `uv run pytest tests/ -q`：**815 全绿**（809 基线 + 6 新增）；`cd web && npm test`：80 全绿（前端无改动，保险跑，未 build）。
2. 单测 §3.4 三组全过：指纹表驱动（加 server / 翻转 enabled / 改 token 两侧 / 改 url 变指纹，无关设置不敏感）；Electron 配置缺失/损坏返回稳定值不抛异常（真实 loader 路径）；get_agent 指纹变化重建（计数+1）/ 不变复用 / 重建后新指纹入账 / 未请求模型键不被牵连；reset_agent_cache 清指纹表后同指纹也重建；指纹计算异常回落上次指纹不阻断。
3. 真机验收留指挥官（§五.3：会话中 add → 不碰设置页不重启 → 下一条消息能调新工具；remove 后下轮工具消失）。

### 说明

- **与规格 §一.2 前提的重要偏差（实施期实锤修正）**：规格称聊天路径三管理工具「从未调用 reset_agent_cache，add 文案描述了一个从未发生的调用」。实施核实：`save_mcp_servers` 共用函数末尾**本就调用 `reset_agent_cache()`**（`crawagent/web/routers/settings/mcp.py:121`，024-027 批次 4abb8e1 引入），三个管理工具经它传递性清缓存——「reset_agent_cache 已触发」文案实际为真，规格把共用函数的清缓存误归于「只有设置页路由」（grep 只查了 mcp_admin_tool.py 本文件，漏了传递调用）。因此 043 的真实价值收窄为：外部改 Electron 配置文件 / token 漂移等**不经过 save_mcp_servers 的路径**从此有指纹门兜底，外加未来新增写路径忘清缓存的双保险。指纹门按规格原样落地；文案对齐改为按真实机制措辞。
- **文案措辞（§3.3）偏差说明**：规格建议改为「下一条消息自动重建工具箱（配置指纹检测）」——基于「reset 从未发生」的错误前提。实际落地采用「配置已落盘并清空 Agent 缓存，下条消息自动重建工具箱…」（描述真实生效链：save 即清缓存 + 下轮 get_agent 重建，指纹门为兜底不写入面向 AI 的回话）。离线分支「或下轮自动重试装入」在指纹门语义下不准确（重建只在配置变化后发生一次，服务届时没起来后续轮不会反复自动重试），改为如实两段式。
- system.md 两处机制描述（工具清单 22 条「takes effect next turn (reset_agent_cache)」+ MCP 硬规则节）经核对与现机制相符（reset 确经 save_mcp_servers 触发），未改动；本轮工具 schema（docstring）零变化，不触发契约同步义务。
- 指纹输入取 `get_settings().mcp_servers`（get_settings 每次新建 Settings，pydantic env 优先 → os.environ 同步快照自动汇入，token 漂移可感知）+ Electron 配置文件原文；`sort_keys=True` 保证 dict 序稳定。规格 §3.1「读不到记 {}」与 §3.2「异常按未变化」分两层落实：文件缺失/损坏 → `_load_electron_mcp_config` 返回 None → 记 {}（稳定值）；计算层异常（get_settings 炸等）→ 返回上次成功指纹。
- 测试计数修正记录：test_get_agent_rebuild_only_requested_model_key 首版把「初始两次构建 + m1 重建」误计为 2，实为 3（最终 m2 重建为 4），已修正——非产品代码问题。
