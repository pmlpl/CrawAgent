## 〇、价值

CrawAgent 是「爬虫员工」，指挥官 2026-10-01 五维评分 80/100，扣分点凝成两件事：**经验不沉淀、报错不换路**。本变更把两件事写成 system.md 硬规则，并顺手修掉 040 评测量出的三个稳定行为缺陷。

- **改动前**：陌生站点每次从零摸索——历史策略/Cookie/脚本明明存在站点档案与知识库里，但「抓前查、抓后存」散在三处弱表述里，模型执行率不稳（040 实锤：多页抓完不问档案直接收工、加 MCP 前不查重名、Cookie 缺失不向用户索取）；工具报错后除了 paywall 场景外没有任何「禁止原样重试」约束，同参数撞墙烧预算。
- **改动后**：抓前「站点档案 + 知识库」双查、抓成功按固定动作沉淀，各是一条 HARD 规则；任何内置工具 ERR 后必须换路（换 UA → 换代理 → 静态/浏览器互换），同参数原样重试被明令禁止；三个稳定 FAIL（06/10/14）连续两场转绿，评测集扩到 20 例，修复前后增量分有数可查。

## 一、背景与问题

### 1.1 经验有库存，但执行契约弱（040 评测实锤）

站点档案（data/sites.json，list_site_profiles / save_site_profile）与知识库（SQLite FTS5，search_knowledge / save_record）**基础设施都是现成的**，相关规则却分散在三处、强度不一：

- 工具清单 #16「ALWAYS call this FIRST when the user asks to crawl a site」（list_site_profiles）；
- Site Profile workflow 节「FOUND → follow the archived strategy」；
- RETRIEVE-FIRST 条（search_knowledge，触发条件限定「content or an answer that might already be in the KB」）。

040 评测基线四跑抓到的三个稳定 FAIL，逐一对上规则缺口：

| # | 现象（040 稳定 FAIL） | 规则缺口定位 |
|---|---|---|
| 06 | extract_list_paged 抓完 15 条直接收工，不 ARCHIVE-ASK 不 save_record | ARCHIVE-ASK RULE 触发列表写了 "multi-page crawl_webpage / extract_list_paged"，但 LIST-page task workflow 第 4 步说 "Present the list to the user"——模型把「展示列表」当任务终点，两节打架 |
| 10 | ask_user 后直接 add_mcp_server，跳过 list_mcp_servers | 「before add (avoid dup name)」只写在工具清单 #21 的描述里，MCP ADMIN 硬规则块没有这条——模型优先服从硬规则块 |
| 14 | list_weread_chapters 返回 WEREAD_COOKIE_NOT_SET 后直接作罢，不 ask_user | WeRead workflow 写 "ask the user to paste their Cookie"，没点名 ask_user 工具；模型要么纯文本索取要么不索取 |

间歇项 01/02（RETRIEVE-FIRST 顺序漂移）同源：检索优先的触发措辞不够硬，预期随本批强化受益（观察项，不单列承诺）。

### 1.2 失败换路缺一般性约束

现有约束只覆盖特殊场景：AUTH/PAYWALL 的 anti-loop 只管 paywall URL；Script escalation ladder S1-S4 只管 run_custom_script 内部；PIONEER MINDSET 管 paywall/VIP/403 的 10 条备选路由。**一般性 ERR（connection refused / timeout / 空壳）之后，「同参数原样重试」没有被任何规则禁止**。

证据标注：这是指挥官 2026-10-01 评估时的观察；040 评测案例 04 的实测序列（crawl_webpage 失败后插入 list_site_profiles 再试浏览器）间接显示失败后的换路动作缺乏稳定次序。按 upgrade-doc「主张带证据」原则，§五.1 设前置验证：先跑 19/20 号新例量出「修复前红基线」，若 5/5 全过（说明现规则余量已够）则如实降级对应措辞强度。

### 1.3 吃 039 红利：KB 半边已经能用

039 的长期记忆蒸馏条目直接进 FTS5 知识库（免五关过滤），search_knowledge 现在真能查到「历史会话沉淀的站点经验」——经验闭环的知识库半边有了实物，站点档案半边一直在。本变更因此**零新基建**：不加工具、不动存储，只做提示词契约的统一与强制 + 评测用例扩容。

## 二、目标

1. **EXPERIENCE LOOP 硬规则**（system.md 新块）：抓前双查（站点档案 + 知识库）、抓后沉淀（站点档案 + ARCHIVE-ASK 入库），收拢 §1.1 的三处分散表述并升级为 HARD。
2. **SELF-HEAL LADDER 硬规则**（system.md 新块）：内置工具 ERR 后禁止同参数原样重试，按 换 UA → 换代理 → 静态/浏览器互换 的阶梯换路，预算沿用现有 PIONEER 数字（单目标总尝试 ≤ 6）。
3. **三个稳定 FAIL 修复**：06/10/14 的规则缺口按 §3.3 逐处补齐（对齐既有机制，不新增机制）。
4. **评测集扩容**：eval_cases.py 新增「经验复用」「失败换路」两类共 5 例（16-20），总量 20 例；修前修后各跑，出增量分。
5. **契约测试同步**：test_prompt_contract.py 的 HARD_RULE_MARKERS 增加 2 个新标记，持续看守新规则不被误删。

**不做什么（划界）**：

- 零新工具、零存储改动：不加 @tool、不动 sites.json / knowledge.db 结构（HANDOFF 明确「提示词契约为主，零新基建」）；system.md 工具清单与 45 计数不动。
- 站点档案保存**维持「用户拍板」**：新站成功后问一次才存（与现状一致），只有跑通的脚本保持「必存不问」——不引入静默自动存档案。
- 不为间歇项 01/02 单列用例、不单独修（随 RETRIEVE-FIRST 措辞强化观察）。
- 不动 042（MCP 工具热感知）、不碰 031 范畴的 middleware 调试 print。
- eval_behavior.py 判定器不改（现有匹配器 + 自定义 check 覆盖全部新例断言）。

## 三、方案设计

### 3.1 EXPERIENCE LOOP（system.md 新硬规则块）

插入位置：RETRIEVE-FIRST 条之后（同属「抓之前」的契约区）。草拟全文（实施时允许微调措辞，标记串 "EXPERIENCE LOOP" 必须保留——契约测试锚它）：

```
- EXPERIENCE LOOP (HARD — check before you crawl, save after you succeed):
  BEFORE the first fetch attempt on any domain in this turn:
    (1) list_site_profiles(origin) — FOUND → follow the archived strategy/notes directly;
        profile has a saved script → run_custom_script with THAT code first, do NOT
        re-analyze the site. NO_PROFILE → normal analysis flow.
    (2) If the request is for CONTENT and past sessions may already have it
        (user hints "之前/上次/有没有抓过" or the topic looks recurring) →
        search_knowledge(...) per RETRIEVE-FIRST scope rules; a covering hit means
        answer from the KB, no re-crawl.
    A re-crawl that a check would have prevented is a violation.
  AFTER a successful crawl of a NEW site (NO_PROFILE was returned earlier):
    ask_user ONCE whether to save a site profile (strategy + notes of what worked);
    only save_site_profile after consent. Content archiving still follows ARCHIVE-ASK
    separately (the two asks may be merged into one question when both trigger).
  A custom script that worked → ALWAYS save_site_profile(script=code,
  strategy="custom_script") immediately, no asking (anchor: existing rule).
```

设计取舍：

- **不改变任何存储与工具**：全部引用现有 list_site_profiles / search_knowledge / save_site_profile / ask_user。
- **新站档案保存保持询问制**：与现状规则一致，本块只是把它并入统一闭环表述；「跑通脚本必存」原文重述作为锚点。两问「允许合并」不是「强制合并」，评测断言对两种形态都兼容（§3.4 案例 18）。
- **RETRIEVE-FIRST 语义不动**：scope 规则照旧，本块只补「抓前查档案」这半边。

### 3.2 SELF-HEAL LADDER（system.md 新硬规则块）

插入位置：Script escalation ladder 之前（失败处理的总纲，脚本阶梯是它 L1 的细化）。草拟全文：

```
- SELF-HEAL LADDER (HARD — a failed fetch must CHANGE something, never repeat):
  When a built-in fetch tool (crawl_webpage / browse_and_crawl / extract_list_paged /
  extract_wallpaper_list) returns ERR / timeout / connection refused / an empty blocked body:
    NEVER retry the SAME tool with the SAME URL and SAME params — an identical retry
    burns budget and returns the same error. Change exactly ONE variable per attempt:
      L1 换 UA/头：run_custom_script S1 with browser UA + Referer + Accept headers.
      L2 换代理：get_proxy() first; pass the returned URL into the script (proxies=...).
         A failed proxied fetch → mark_proxy_failed(host, port, reason) IMMEDIATELY,
         then the next get_proxy skips it; NO_PROXY → fall back to direct, do not loop.
      L3 换路线：static 与 browser 互换（crawl_webpage 因网络原因失败 → browse_and_crawl
         一次；浏览器路线失败 → 降级静态脚本），或走 PIONEER MINDSET 的 P 路由。
    Budget: total attempts per target URL ≤ 6 (PIONEER guardrail). Inside
    run_custom_script the S1-S4 ladder and its 4-segment cap still apply.
    After the ladder is exhausted, report which level failed with what error and ask
    the user how to proceed.
  Exceptions (these existing rules OVERRIDE this ladder, do not double-handle):
    SPA shell → run_custom_script directly (browse_and_crawl forbidden as next step);
    LOW CONFIDENCE → browse_and_crawl re-fetch (SUPERVISOR rule);
    paywall/VIP/403 → AUTH/PAYWALL ladder and PIONEER routes.
```

设计取舍：

- **本块是「收拢 + 泛化」，不是新机制**：把 paywall anti-loop 的「同 tool+URL 不许撞两次」泛化到一般 ERR；换 UA（S1）、换代理（PROXY RULE）、换路线（TOOL CHOICE / PIONEER）全部引用既有规则。
- **例外块防打架**：SPA 壳规则（03 例锚点）、SUPERVISOR（08 例锚点）、AUTH/PAYWALL 的优先级显式声明，避免新块把老用例改坏——§五.3 全量回归就是验这个。
- HANDOFF 原文「静态降级/浏览器兜底」落成 L3 的 static 与 browser 互换。

### 3.6 边界与回退

- **新规则可能改坏老用例**：EXPERIENCE LOOP 会让模型在更多场景先调 list_site_profiles——老用例的 expect_seq 是宽进子序列，插入调用不破坏断言；但 12/13（零工具）必须保持零调用（寒暄/概念题无抓取意图，LOOP 不触发）。若全量回归出现老例 FAIL：按 040 门槛「同例连续两次 FAIL 才算真回归」，先修措辞再考虑判据校准，不静默放宽。
- **修复前红基线可能不红**：§五.1 若 16-20 首跑全过，说明现有规则余量已够，如实报告并把对应新块降级为收拢性表述，不硬造增量。
- **prompt cache**：SYSTEM_PROMPT import 时读盘、字节级静态，改 system.md 后新进程自然生效（040 已验证该机制），无需热更处理。
- **评测成本**：20 例 × 平均 20-40s × 2 场，每场约 10-15 分钟真 LLM 调用；--filter 支持只跑新例。

## 五、验证方式

1. **修复前红基线（先测痛点，前置验证硬门槛）**：只加 16-20 用例、不动 system.md → `--filter` 跑 16-20 记录通过数。预期 ≤ 2/5（痛点真实）；若 5/5 全过 → 如实报告，§3.1/3.2 对应新块降级为收拢性表述，重估本变更范围后再继续。
2. **契约测试**：uv run pytest tests/ -q 全绿（新标记 2 个在位、45 计数与工具清单不变）。
3. **三稳定 FAIL 转绿**：全量 20 例跑 ≥ 2 场 → 06/10/14 连续两场 PASS（040 回归门槛）；老用例无新增稳定 FAIL。
4. **增量分入账**：修复前基线分 vs 修复后全量分写进实施记录（16-20 修复前 N/5 → 修复后 M/5；06/10/14 由稳定 FAIL 转 PASS）。
5. **无副作用**：评测跑完 data/sessions/、data/knowledge.db、output/、downloads/ 无新增（桩拦截写路径，同 040 §五.5）。
6. **实施记录随代码入库**：git add 只列明确路径；000-目录.md 回写状态与 commit 号。
