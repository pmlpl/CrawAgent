## 〇、价值

- **改动前**：用户说"把这个列表每一页都抓下来"，AI 只能现场写一个 Python 脚本逐页请求（run_custom_script 路径）——烧 token、慢、每次重写；内置工具里只有壁纸工具会翻页，别的列表站用不上。
- **改动后**：静态分页的列表站，AI 调一次 `extract_list_paged(url)` 就把所有页的条目收齐去重，不用写脚本。

## 一、背景与问题

- 全项目唯一会翻页的代码藏在 `wallpaper_tool._auto_paginate`：猜 `page/p/pageNum` 三种 URL 参数、上限 20 页、"没有新链接即停"，且提取逻辑绑定壁纸站的卡片结构，无法复用。
- 通用列表工具 `extract_list` 是纯解析器（收 HTML 字符串、不管抓取），设计与契约都不含翻页。
- 通用批量抓取完全依赖 AI 写脚本（BATCH-FIRST 规则缓解），静态翻页这种**确定性机械劳动**不值得每次让 LLM 现写。
- 范围经 grilling 拍板：**本次只做翻页**；"深度爬取"（进详情页二次提取）是语义活，脚本模式已验证可行，不通用化——结论沉淀为 **ADR-0002**。

## 二、目标

1. 共享翻页模块，两种策略：下一页链接追踪（rel=next / class 含 next / 「下一页」文案）优先，退回 URL 参数猜测（page/p/pageNum，命中的参数粘性沿用）。
2. 新工具 `extract_list_paged(url, limit, max_pages)`：翻页 + 每页正则抽取 + 跨页去重，一次调用返回全列表。
3. wallpaper_tool 收编进共享模块（行为为原实现的超集）。
4. **不做**：JS 渲染分页（加载更多/无限滚动）——需要浏览器执行，是另一个世界，明确留给 browse_and_crawl / playwright MCP / 脚本；深度爬取通用化。

## 三、方案设计

- **walk_pages 生成器**：逐页产出（页 URL、HTML、本页新条目 URL）。终止条件三个：本页无新条目、翻满 max_pages、抓取失败。下一页链接失效时自动退回参数猜测。
- **参数探测带"验货"**：猜出的分页参数页要先抓下来验一遍"确实翻出了新条目"才采纳并粘住该参数——防止第一个无效参数（如站点不认 `?p=`）就把翻页判死。
- **提取策略分工**：翻页终止判断与条目提取都用轻量正则阶段（重复 a 链接模式）；单页任务仍走 extract_list 的三段式（正则→LLM→DOM），互不侵蚀契约。
- **节流**：所有抓取走 `_enforce_delay()`（request_delay 是全项目唯一限流手段），wallpaper_tool 收编后顺带获得此前没有的节流。

## 八、实施记录（2026-09-06）

### 怎么做到的（人话版）

整个功能的核心是一个**"边走边看"的循环**：从第一页出发，每翻一页都把页面上认得的条目记在小本子上；翻到新一页如果发现小本子上已经全有了，说明到底了（或参数是假的），停。找下一页先看页面上有没有"下一页"按钮（最可靠），没有就试常见的页码参数——**试一个参数要真的翻出新东西才算数**，并且一旦试对了就记住它，后面每页都用同一个参数，不再每个参数都瞎试一遍。

三个踩过的坑：
- **测试夹具的相对路径**：夹具里写 `href="page/3/"`，直觉上觉得会跳到 `/posts/page/3/`，实际 URL 拼接规则是相对"当前页所在目录"解析，得到 `/posts/page/2/page/3/`——测试报错后换成根相对路径 `/posts/page/3/` 才对。真实站点的相对分页链接同理，这是 walk_pages 用标准 urljoin 的原因（行为正确，是直觉错了）。
- **"无新条目即停"的边界**：第 2 页若与第 1 页条目完全相同（参数无效时站点常返回第 1 页内容），会被参数探测阶段直接否掉、不采纳也不产出——测试最初期望"产出第 2 页但条目为空"，与实现对不上，复核后确认实现是对的、期望写错了，修的是测试。
- **工具吞噬尖括号**：写测试断言时含尖括号的内容会被编辑工具吞掉，改用 Python 脚本落盘（项目已知坑，见长期记忆）。
