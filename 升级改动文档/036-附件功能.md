## 〇、价值

- **改动前**：聊天输入区的「添加附件」按钮自插件化重构（57f919f）起就是**纯占位**——没绑任何点击事件，指挥官实测点击无反应。用户无法把本地文件（导出的 json、日志、代码、文档）喂给 AI。
- **改动后**：点「添加附件」弹系统文件选择框，选中的文件上传到服务端，输入框上方显示附件 chip；发送后 AI 拿到附件路径清单，用新工具 `read_file` 读取内容（大文件分段读），本地文件从此进入对话。

## 一、背景与问题

1. ChatComposer.vue:179 的「添加附件」按钮无 @click 处理器，是个自第一版就存在的摆设。
2. 项目现状 **AI 没有任何读本地文件的工具**（file_tool.py 只有 save_to_file；run_custom_script 能绕道但不该让 AI 写脚本读文件），附件功能必须配套 `read_file` 工具。
3. 已知坑：`_truncate_tool_message`（middleware.py:151）对**所有** ToolMessage 一刀切裁剪（`tool_result_max_chars=2000`，保头 1000 + 尾 500）——read_file 一次返回大文件会被裁掉中间，必须支持分段读。
4. FastAPI 处理 multipart 上传需要 `python-multipart` 依赖（当前未安装）。

## 二、目标

1. 「添加附件」按钮激活：点击弹系统文件选择框（可多选）→ 上传 → 输入框上方附件 chip 列表（文件名 + 大小 + × 移除）→ 随消息发送。
2. 新工具 `read_file`：AI 读本地文本文件，支持 offset/limit 分段（大文件多轮读全），单次返回超限自动截断并提示剩余量。
3. pdf/docx 等二进制格式：read_file 返回乱码/二进制提示，引导 AI 改走 `markitdown_convert`（009 已有工具）转换后读取——本变更不重复造转换轮子。
4. **不做**：图片视觉理解（主模型可能无视觉，第一版图片附件仅作为文件存在，AI 可复制/改名但"看图"不在范围，记 §六）；附件自动清理策略；拖拽上传（§六）。

## 三、方案设计

### 3.1 后端：上传端点 `POST /api/uploads`

- multipart 接收（`file: UploadFile` + `session_id: Form`）；依赖 `python-multipart` 加入 pyproject。
- 落盘：`data/uploads/<session_id>/<清洗后文件名>`——文件名过 `sanitize_dirname` 同款清洗（非法字符转 _）；重名自动追加序号 `-1`、`-2`（防覆盖）；目录自动创建。
- **落 data/uploads/ 的理由**：附件是输入材料不是产物（不进 output/downloads，不参与保留清理策略）；与 ADR-0001（背景图存 data/）同一保管逻辑。
- 大小上限 50MB，超限返回人话错误；返回 `{ok, name, path, size}`（path 为服务端绝对路径，后续注入消息用）。
- 路径安全：落点恒在 data/uploads 内校验（is_relative_to），防文件名构造逃逸。

### 3.2 新工具 `read_file(path, offset=0, limit=20000)`

- 挂 file_tool.py（与 save_to_file 同文件，@tool 自动发现；`_TOOL_META` 补 category）。
- 语义：读 path 文件的 [offset, offset+limit) **字符**区间返回，编码 utf-8（errors=replace）；返回尾部带 `（共 N 字符，已读 a-b，继续读传 offset=b）`提示，AI 据此分段；offset 超界返回空串 + 结束提示。
- 单次 limit 硬上限 50000 字符（防单次调用撑爆上下文）；默认 20000。
- 不存在的路径 → 人话错误；二进制内容（含 \x00 或解码失败率高）→ 提示"疑似二进制文件，pdf/docx 请用 markitdown_convert 转换"。
- 安全面说明：与 run_custom_script 等价（本来就能读任意文件），不新增攻击面；不做目录白名单。
- 034 安全校验的关系：read_file 读任意路径是**有意设计**（附件在 data/uploads、但用户可能让 AI 读项目里其它文件）；work_dir 逃逸校验只管**写**工具，不影响读。

### 3.3 消息注入（chat_ws）

- send 载荷新增 `attachments: [{name, path, size}]`；chat_ws 收到后在用户消息 content 尾部追加固定格式块：

  ```
  [附件]（用 read_file 工具读取内容；pdf/docx 二进制用 markitdown_convert 转换后再读）
  - <path>（<name>，<size>）
  ```

- 注入的是路径清单而非文件内容（上下文经济性；内容 AI 按需读）。无附件时零改动。

### 3.4 前端（ChatComposer + useChat）

- ChatComposer：占位按钮绑 @click → 触发隐藏 `<input type="file" multiple>`；change 后逐个 `POST /api/uploads`（带当前 session_id），上传中按钮转圈（复用 busy 模式：spinner 绝对定位不撑宽）。
- 附件 chip 列表（输入框上方）：`name (size) ×`；× 移除仅从前端列表去掉（不删服务端文件，重传靠重名序号防覆盖）。
- useChat：`attachments` ref 数组 + `addFiles/removeAttachment/clearAttachments`；send 载荷带 attachments（空数组不带键），发送成功即清空。
- busy / 发送中禁用附件按钮（防中途改清单）。

### 3.5 system.md 契约同步

- 工具清单 +read_file（**条数同步**，_TOOL_META category=文件）。
- 附件处理规则：收到 [附件] 块 MUST 先 read_file 再回答/处理；大文件按提示分段读全；pdf/docx 走 markitdown_convert；附件内容涉及用户数据，save_record 入库前照 ARCHIVE-ASK 问。

### 3.6 测试

- 后端：uploads（成功/重名序号/超 50MB/文件名清洗/落点校验）；read_file（全文/分段 offset/limit 硬上限/不存在/二进制提示）；chat_ws 注入格式（有附件/无附件不带键）。
- 前端：按钮触发 file input、chip 渲染与移除、载荷带 attachments、发送后清空、busy 禁用。
- 基线：700 pytest + 57 vitest 起算同步计数。

## 八、实施记录（2026-09-30）

### 怎么做到的（人话版）

四块落地：

1. **上传端点（`crawagent/web/routers/uploads.py`，server.py 挂载）**：`POST /api/uploads`（multipart：`file` + `session_id`）。落盘 `data/uploads/<session_id>/<清洗后文件名>`——附件是输入材料不是产物，不进 output/downloads（不参与保留清理策略），与 ADR-0001（背景图存 data/）同一保管逻辑。文件名过 `sanitize_filename`（复用 session_dir 的 `_INVALID_CHARS` 正则，但**保留扩展名**——AI 靠它判断 pdf/docx 走 markitdown_convert，且不 strip 点）；重名 `_unique_target` 自动加 `-1`、`-2` 序号防覆盖；大小上限 50MB（边写边数，超限截断 + 删残文件 + 人话错误）；落点恒在 data/uploads 内 `is_relative_to` 双保险（session_id 先过 `[^\w.-]` 正则清洗，构造逃逸直接拒）。
2. **read_file 工具（`crawagent/tools/file_tool.py`，@tool 自动发现）**：读本地文本文件，`offset/limit` 分段——返回尾部带"（共 N 字符，已读 a-b，继续读传 offset=b）"提示，AI 据此接力读到"已全部读完"；limit 硬上限 50000 字符（防单次调用撑爆上下文）。二进制检测两路：raw head 含 `\x00` → 提示走 markitdown_convert；解码 `\ufffd` 占比 > 30% → 疑似非 UTF-8 同样引导。**读任意路径是有意设计**（附件在 data/uploads，但用户可能让 AI 读项目里其它文件），与 run_custom_script 能力面等价，不新增攻击面；work_dir 逃逸校验只管写工具，不影响读。`_truncate_tool_message`（middleware）对所有 ToolMessage 一刀切裁剪到 ~2000 字符保头尾——read_file 单次返回大文件会被裁中间，所以分段读全 + 尾部提示是硬要求，docstring 与 system.md ATTACHMENT 规则都强调。
3. **消息注入（chat_ws）**：send 载荷 `attachments=[{name,path,size}]` 时，`_build_attachment_block`（server.py 纯函数，可单测）拼成 `[附件]（用 read_file 工具读取内容；pdf/docx 二进制用 markitdown_convert 转换后再读）\n- <path>（<name>，<size> 字节）` 块追加到用户消息尾部。注入路径而非内容（上下文经济性，AI 按需 read_file）；无附件/全非法条目返回 None 零改动。**抽成纯函数**是为了离线单测（chat_ws 是 WS 端点，发消息即触发真实轮次，离线测不了，与 034/035 WS 层缺口同源）。
4. **前端（ChatComposer + useChat）**：占位按钮绑 `@click` → 触发隐藏 `<input type="file" multiple>`；change 后逐个 `POST /api/uploads`（FormData 带 `chat.session`），上传中按钮转圈（busy 模式：spinner 绝对定位居中 + label visibility 藏形保占，按钮尺寸不撑宽，照抄 SettingsModels `.btn-busy`）。附件 chip 列表（输入框上方）：文件名 + 大小 + × 移除（仅从前端列表去，不删服务端文件，重传靠重名序号防覆盖）。useChat 加 `attachments` ref + `addAttachment/removeAttachment/clearAttachments`；send 带 attachments（空数组不带键），发送成功即清空；切会话/新会话清空清单。busy/上传中禁用附件按钮（防中途改清单）。

### 说明（与规格偏差）

- **附件注入块抽成纯函数 `_build_attachment_block`**：规格 §3.3 写在 chat_ws 内联；为可离线单测（WS 端点离线测不了），抽到 server.py 顶层纯函数，chat_ws 调用它。行为零差异，可测性提升。
- **read_file 解码失败率阈值 30%**：规格只说"含 \x00 或解码失败率高"未给数；实现取 `\ufffd` 计数 > max(64, len*0.3)——纯 ASCII/UTF-8 文本不会误判（0 个替换符），latin-1 坏字节文件（0xff*1000）触发。阈值用真实坏文件校准，未发现误报。
- **python-multipart 已在 venv**：`uv pip list` 显示 0.0.32 已装（可能被其他依赖间接拉入）；pyproject 声明补 api extra 是为 fresh install 显式化，`uv pip install` 无新增（幂等）。
- **附件按钮 busy spinner 复用 032 批次定的模式**：spinner 绝对定位居中 + label visibility 藏形保占，按钮尺寸不因 loading 撑宽——照抄 SettingsModels.vue `.btn-busy`，组件内本地定义（settings.css 规则挂 `.settings-page` 前缀不可跨用）。
- **图片视觉理解不做**（§六）：第一版图片附件仅作为文件存在，AI 可 read_file（二进制提示）或复制/改名，"看图"不在范围；033 能力池接入真视觉模型后可转 use_vision 流程扩展。
