## 〇、价值

- **改动前**：开启 `THINKING_DEPTH` 后，AI 思考阶段前端只有 "deeply exploring" 转圈，几十秒空等；思考内容只在 AIMessage 完成后整块冒出（折叠块）。原因是 turn_engine 的 token 级流式分支只转发了 `chunk.content`，完全丢弃 `chunk.additional_kwargs.reasoning_content`，推理 token 被白白漏掉。
- **改动后**：推理模型的思考 token 逐块推给前端（`ai_thinking_delta`），轨迹里实时滚动；思考结束发 `ai_thinking_done` 收尾折叠。用户不再干等，能看到 AI 边想边吐字。

## 一、背景与问题

1. **流式断点**：`turn_engine.py` 的 `stream_mode=["messages"]` 分支只处理 `chunk.content`（可见回答），不读 `reasoning_content`。
2. **整块兜底**：`values` 快照分支在 AIMessage 完成时一次性读 `msg.additional_kwargs.reasoning_content` 推 `ai_thinking`——所以是"思考完才一口气出现"，不是"边想边流"。
3. **默认思考关**：`THINKING_DEPTH=off` 时根本不产生 `reasoning_content`，本变更只对开启思考的推理模型生效（off 行为不变）。

## 二、目标

1. 后端：`AIMessageChunk` 携带的 `reasoning_content` 增量逐块推送（新事件 `ai_thinking_delta`）。
2. 后端：AIMessage 快照到达时，若该 id 已流式推送过，只发 `ai_thinking_done` 结束信号，不重发整块（防覆盖前端累积文本）。
3. 前端：`ai_thinking_delta` 复用同 id 的 thinking step 逐块追加；`ai_thinking_done` 收尾；`pushToolCall` / `endTurn` 兜底强制收尾（防后端异常未发 done 残留 streaming 态）。
4. UI：思考 `<details>` 在 streaming 时自动展开 + "流式中…"指示；streaming 结束后由用户手动控制开合（`@toggle` 同步 `_opened`）。
5. **不做**：非推理模型（off / openai 中转站）的思考——它们没有 reasoning_content，走原 `ai_thinking` 整块 + plan 兜底路径不变。

## 三、方案设计

- **事件协议新增**：
  - `ai_thinking_delta {type, id, delta}` — 推理 token 增量，逐块推送
  - `ai_thinking_done {type, id}` — 该条思考流结束，前端收尾折叠
  - 原 `ai_thinking {type, id, content}` 保留，用于非流式兜底（非推理模型 / 工具调用前的 plan 文本）
- **去重**：`streamed_thinking: dict[msg.id, str]` 记录已流式推送的 id；快照分支命中即发 done 跳过整块。`plan`（content 里的工具调用计划）由原有 `is_plan_content` 去重分支处理，不在此重复。
- **前端安全网**：`_finalizeOpenThinking()` 在 `pushToolCall`（工具开始 = 上一段思考已结束）与 `endTurn`（轮次结束）调用，把任何残留 `streaming=true` 的 thinking step 收尾——后端漏发 done 时也不卡在展开态。
- **UX**：`<details :open="step.streaming || step._opened" @toggle="step._opened = $event.target.open">`——streaming 时强制展开让用户看流；结束后交还控制权给用户。

## 五、实施记录（人话版）

1. **后端转发 reasoning**：在 `messages` 流式分支里，`AIMessageChunk` 先读 `chunk.additional_kwargs.reasoning_content`（逐块 delta），有就累加进 `streamed_thinking[chunk.id]` 并发 `ai_thinking_delta`；原来的 `chunk.content` 处理原样保留。顺序上 reasoning 块先于 content 块到达，所以 `started_llm_ids` 起点判定也覆盖到了思考起点。
2. **快照分支分流**：原来无脑发整块 `ai_thinking`。改成先看 `msg.id in streamed_thinking`——是就只发 `ai_thinking_done`（前端收尾），不走整块；否则走原 `ai_thinking` 整块路径（非推理模型 / plan 兜底）。打印日志区分 `streamed done` 与整块 source。
3. **前端累积**：`pushThinkingDelta(id, delta)` 找同 `_thinkId` 的 thinking step，找到就 `content += delta`，没有就建一条 `streaming: true` 的。`finishThinkingStream(id)` 把 `streaming` 置 false。原 `pushThinking` 加可选 `id` 参数：若已有同 id 的流式 step，只收尾不重复建（防御性，正常路径后端会发 done 而非整块）。
4. **安全网**：`pushToolCall` 开头调 `_finalizeOpenThinking()`——工具一开始，上一段思考必然结束；`endTurn` 也调一次。这样即便后端漏发 `ai_thinking_done`，前端也不会有永远 streaming 的 step。
5. **UI 展开**：CrawlTrace 的思考 `<details>` 加 `:open="step.streaming || step._opened"` 和 `@toggle` 同步 `_opened`。streaming=true 时强制展开（用户想看流，被撑开正是目的），结束后 `_opened` 接管——用户展开过就保持展开，没碰过就收起。加了 "流式中…" 脉冲小标签和 `.thinking-pre.streaming` 实线边框做视觉区分。
6. **测试**：加用例 4b（3 个 delta 累积成 1 条 step、done 收尾、tool_call 同 trace）和 4c（流式中途收到 tool_call 无 done，安全网兜底 streaming=false）。原 7 vitest → 9 vitest。

## 七、修订（2026-09-07，第二轮：修"思考与正文重复显示同一文本"）

实测后发现：开启思考后，同一段推理文本既出现在轨迹 thinking step 里、又出现在正文 AI 气泡里。根因是部分供应商把同一推理文本**同时写进 `chunk.content` 与 `chunk.additional_kwargs.reasoning_content`**，原流式分支两边都转发 → 双写双显。修法三处：

1. **流式分支改 `elif`（互斥）**：一个 chunk 若带 `reasoning_content`，它就是思考 chunk，其 `content` 是同一文本的双写，不再当回答推 `ai_delta`。安全：正常路径（reasoning 在 additional_kwargs、content 空）行为不变。
2. **快照去重扩展**：原 `is_plan_content` 只处理 `content == plan` 的工具调用计划文本重复。扩展为 `_content_dup_with_thinking`：reasoning 非空且 content 与之重合（相等或 content 以 reasoning 为前缀）时，content 也不是独立回答，丢弃 `ai` 推送并清掉 `streamed_ai` 残留。
3. **`finishThinkingStream` 前端去重**：流式思考结束（`ai_thinking_done`）时，若正文里残留了同内容的 AI 卡片，移除。修了一个 reactive proxy 坑：`aiStreams` 存原始对象、`items` 里是 reactive 代理，`v === tail` 身份比较恒不等 → 改为直接 `aiStreams.delete(id)`。
4. vitest 加用例 4d（双写场景：思考 step 保留、同文 AI 卡移除、后续真实回答建新卡）。7→10 vitest。
