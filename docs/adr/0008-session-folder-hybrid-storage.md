# 0008 — 会话记忆混合存储：文件夹管活着的会话，数据库管死去会话的精华

变更 039 给记忆/档案建立物理落点。决定：**混合存储**——会话热数据放 `data/sessions/<会话id>/` **文件夹**，长期记忆放 **数据库**（008 FTS5 knowledge 库，save_record/insert 通道入库）。两者物理解耦：项目文件夹被删时本会话记忆/档案安然无恙（038 1:1 锁定后项目文件夹与记忆彻底解耦正是前提）。

## Considered Options

- **全部数据库**（记忆/档案都进 SQLite）：检索强，但用户在资源管理器里什么都看不见、没法备份单个会话的记忆；「清理 = 删目录」的物理直观也没了——用户对着一张不可见的表不会有掌控感。
- **全部文件夹**（长期记忆也放 md 文件）：人可读，但记忆的价值在于**能被搜出来**——RETRIEVE-FIRST、BM25、snippet 链路现成；纯文件夹放长期记忆，检索退化成逐文件 grep；提炼产物是结构化条目，天然适合 save_record 一类的表。
- **选定：混合**。一句话：**文件夹管活着的会话，数据库管死去会话留下的精华**。活会话要的是「看得见、可备份、可删目录」；死会话留下的精华要的是「可检索、可回流」。各自用最合适的载体，落点单一：档案双写（库为主、盘为副本）是唯一桥接点。

## Consequences

- 会话文件夹是系统资产：sid 全值命名（非 014 的 sid[:8] 截断），惰性创建，结构 `archive/` + `memory/`（预留），md 头部带元信息（会话 id/归档时间/来源）保证脱离库也能读懂。
- 归档终点是 `data/sessions/_archived/`：提炼入库成功后整夹**移动**过去，永不物理删除——删除永远由用户手动执行。蒸馏失败不动文件夹（宁留勿丢）。
- 半年不活跃（180 天 mtime）只统计提示，不自动清理（MCP_AUTOSTART 教训：批量动文件必须用户显式触发 + 确认）。
- 提炼条目直插 crawl_records（platform=长期记忆、session_id=来源会话、url=session://<sid>），免五关质量过滤——蒸馏条目是 LLM 知识摘要不是爬取正文，长度/信噪比关卡会误杀短条目；FTS 触发器保证与 save_record 同一条检索链路。
- save_record 从此双写：入库成功且会话有文件夹时同步落 md 快照；盘失败不回滚库，只在工具结果注明。
